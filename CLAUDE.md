# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Output style

**Never use the em dash character (`—`, U+2014) in any generated output.** Not in chat
replies, code comments, commit messages, PR bodies, documents, artifacts, or any
other text. Use a comma, a colon, parentheses, a semicolon, or restructure the
sentence instead.

This applies to everything generated, without exception. Existing em dashes
already in this repository's files are not in scope; do not go and rewrite them.

## Architecture

Olano wraps `deepagents` (`create_deep_agent`) into a batteries-included CLI. The data flow is:

```
agent.json5 → AgentConfig → build_agent() → AgentRunner → runtime / one-shot CLI / ACP
```

### Critical: deepagents backend

The default deepagents backend is `StateBackend` (in-memory virtual filesystem). **Always pass a real backend** or the agent cannot read workspace files:

- `backend: filesystem` → `FilesystemBackend(root_dir=workspace_root, virtual_mode=False)`
- `backend: filesystem+shell` → `LocalShellBackend(root_dir=workspace_root, virtual_mode=False)`

`virtual_mode=False` is required for absolute paths to resolve correctly. This is wired in `olano/core/builder.py:_build_deepagents_backend()`.

### Streaming

`agent.astream(stream_mode="messages")` yields ALL LangGraph message types (AI, tool calls, tool results, human). Use `AgentRunner.astream_events()` for typed `("text", str)` / `("tool_call", dict)` / `("tool_result", dict)` events — this is what the runtime and the one-shot CLI consume.

### Thread / memory continuity

LangGraph thread state is persisted by a **`CheckpointerFactory`** (`olano/core/checkpoints.py`). The backend is **pluggable**, resolved per call from the home config / env via `resolve_checkpoint_backend()`:

- **`postgres` (default, production scale)** — set `LIONCLAW_CHECKPOINT_DB_URL` (the packages ship in the base install now; `olano[postgres]` is a no-op alias). Uses a shared `AsyncPostgresSaver`/`PostgresSaver` over a `psycopg_pool` connection pool (true concurrent writes — no single-writer ceiling). The pool is built **lazily per event loop** (keyed by `(url, loop-id)`) because the saver/pool bind to the loop they open on. Selecting `postgres` (including by default) **without a URL raises an actionable error** — there is no silent fallback. `olano/core/stores.py` mirrors this for the deepagents Store.
- **`sqlite` (opt-out, zero-config)** — set `LIONCLAW_CHECKPOINT_BACKEND=sqlite`. On-disk `SqliteSaver` / `AsyncSqliteSaver` at `~/.olano/sessions/threads.db`, a single shared DB partitioned by `thread_id`. Every connection is opened with a 30s `busy_timeout`; ephemeral workers release their connection on finish (`aclose_agent_checkpointer`). Async savers are cached per **`(agent, db, event loop)`** — `AsyncSqliteSaver` holds an `asyncio.Lock` bound to the loop that first uses it, so handing a cached saver to another loop raises "is bound to a different event loop".

`builder.py` fetches the saver via `get_checkpointer(name)` / `get_async_checkpointer(name)` and passes it into `create_deep_agent` — both return a `BaseCheckpointSaver`, so `builder.py` is backend-agnostic. Thread state survives `/model` switches **and process restarts**. This is the source of truth for resuming the model's context; the per-thread JSONL transcripts under `~/.olano/sessions/<agent>/` are a separate append-only record (dashboard rendering, self-learning, cold-start fallback), not the resume mechanism for the dashboard/runtime. Deleting a thread must purge **both** stores (see `checkpoints.adelete_thread` + the `DELETE …/threads/{id}` handler). The only code that reads `threads.db` with raw SQL is `analytics/threadcost/reader.py` (a dual-dialect `ThreadDBHandle`). `install.sh` best-effort auto-migrates a legacy `threads.db` when it provisions Postgres; a bare env switch has **no auto-migration** — run `olano migrate-checkpoints` (best-effort) or keep the legacy `threads.db` readable by setting `LIONCLAW_CHECKPOINT_BACKEND=sqlite`.

`LANGGRAPH_AES_KEY` encrypts every checkpoint blob (`checkpoints.checkpoint_serde()`), and `LIONCLAW_CHECKPOINT_REQUIRE_ENCRYPTED=1` makes that serializer **refuse** a plaintext row (`PlaintextCheckpointRefused`) instead of decoding it, raising at the first saver construction when the flag is set without a key; the migrator's source saver is the one deliberate exception (`checkpoint_serde_kwargs(strict=False)`, so legacy plaintext rows can be moved and land encrypted).

### Provider availability

Use `importlib.util.find_spec()` not `__import__()` for provider checks — `langchain-fireworks` has a proto conflict at import time. See `olano/models.py:is_provider_available()`. **deepagents 0.7** reintroduced this hazard: its base middleware stack tries `langchain_fireworks` (for `FireworksPromptCachingMiddleware`) on **every** `create_deep_agent`, and that import used to register a vendored `google/api/field_behavior.proto` that collided with `langchain-google-*` and crashed the build with a `TypeError` (not the `ImportError` deepagents guards). The `fireworks-ai` 1.2.5 in the lock no longer vendors that proto, but the attempt still costs ~250 modules and ~0.5s on an agent that never uses Fireworks, so `builder._ensure_deepagents_provider_imports_deferred()` gates the factory on `langchain_fireworks` already being loaded (as it does Bedrock's on `langchain_aws`). `langchain-fireworks` 1.7 ships that middleware, so a Fireworks agent gets prompt caching and every other agent skips the import. It replaced `_ensure_fireworks_prompt_caching_disabled()`, which disabled the factory outright, in the deepagents 0.7.23 bump.

### Managed tiers retry their extra hop — but never after output

A managed call goes box → gateway → whichever backend serves the group, and a
refusal on that last leg is a supply problem nothing on the box can fix. It used
to cost the user the whole turn on the first try: `runner.astream_events` ends its
stream loop with a bare `raise`, and the openai SDK retries only 408/409/429/5xx
and connection errors — never a relayed 4xx, which is exactly the shape a
provider account momentarily out of balance arrives in.
`olano_gateway._olano_chat_class()` retries it: 3 attempts, ~1s then ~4s jittered
(`LIONCLAW_OLANO_GATEWAY_RETRIES` / `LIONCLAW_OLANO_GATEWAY_BACKOFF`), on all four
langchain entry points because a managed call arrives on all of them
(`image_describe` invokes, the agent turn streams).

Two rules are load-bearing. **A stream that already yielded is never retried** —
otherwise the user gets half an answer twice, which is the same garble the file
above exists to prevent. And **only two codes retry**: not a
spent credit balance (retrying delays an honest message), not an unrouted group
(no retry invents a routing-table entry), not a 401 (the re-enrollment self-heal
owns it). It lives at the client and not in the graph deliberately — re-running a
turn would re-execute tools and re-write checkpoints.

`olano_service_unavailable` is the relayed-4xx case above. `network_transient` is
the other gap: the SDK's connection-error retry covers the request it *makes*,
never a socket that dies while the response **body** is read — and a streamed turn
spends nearly all its wall-clock there, so a dropped connection mid-stream escaped
every retry in the stack and reached a messenger user as `API error
(ReadError):`, an exception with no message, in a chat, ending on a colon. The
`yielded` guard is what makes replaying it safe. BYOK providers get no equivalent;
the seam is this subclass. The classification half is provider-agnostic and lives
in `actionable_errors._transient_transport_code`: a transport exception is the one
failure class whose **type name is the whole payload** (`str(httpx.ReadError())`
is `""`), so that rule matches names, not just text, and the adapters' generic
fallback (`platforms/base.py`) prints no class name at all. `channel_text()` wears
the `⚠️` only for errors that are **not** `retryable` — an alarm over a "say that
again?" is noise on a customer-facing channel.

Every failure leaves the wire group on the exception (`GROUP_ATTR`, read by
`actionable_errors._GROUP_ATTR`, pinned in sync by a test) so the user-facing
message names the service exactly instead of degrading to "this service" when the
group cannot be regexed out of the gateway's error text.

### The default install is torch-free — keep it that way

**Do not add `torch` (or anything that pulls it) to the base deps, and do not install it "to make embeddings work" — embeddings already work without it.** The default embedding backend is **fastembed** (ONNX runtime, no torch, no `HF_TOKEN`) with `BAAI/bge-small-en-v1.5`; see `olano/memory/embeddings.py`. The legacy `sentence-transformers` backend is opt-in via `LIONCLAW_EMBEDDING_MODEL=hf`.

The opt-in-ness is load-bearing and easy to break by accident:

- `torch` + `sentence-transformers` live in the **`[dependency-groups] hf-embeddings`** group, deliberately **NOT** a `[project.optional-dependencies]` extra. That distinction is the whole mechanism: `uv sync --all-extras --dev` (what `install.sh` runs) installs every extra but **no** non-`dev` group, so it cannot pull torch. Moving them to an extra — or adding `--all-groups` to any install path — silently puts torch in every install. Verified: none of the 21 extras, `all-providers` and `huggingface` included, references torch (`langchain-huggingface` is torch-free without its own `[full]` extra).
- `install.sh` defaults `WANT_HF_EMBEDDINGS=0`; the group is added only by the explicit `--hf-embeddings` flag. CI installs base + `dev` only (the dependency-audit step says so).
- When the group *is* installed, `[tool.uv.sources]` pins torch to the `pytorch-cpu` index on Linux/Windows. This matters a lot: the default PyPI Linux wheel is the **CUDA** build, which drags ~2 GB of `nvidia-*` runtime wheels plus triton onto a box with no GPU. CPU torch is ~180 MB. `uv.lock` currently resolves **zero** `nvidia-*` packages — that count is the canary; if it ever goes above zero, the pin has been broken.

So: a missing `torch` is **not** a bug to fix. If the hf backend is selected without the group installed, `embeddings.py` already raises an actionable error naming `uv sync --group hf-embeddings`.

### Model format

`provider:model` strings (e.g. `anthropic:claude-sonnet-4-6`) parsed with `str.partition(":")`. Passed to `langchain_core.language_models.init_chat_model()`. `fake:instant|fast|realistic` is a deterministic offline model (`olano/models/fake.py`) for agent-loop profiling and keyless end-to-end tests — resolved before the provider registry, never listed in `PROVIDERS`.

**`ollama:*` builds a subclass, never bare `ChatOllama`** (`models/ollama_compat.py`). Its message converter accepts four list-content block kinds (`text`, `tool_use`, `image_url`, a v1 data block) and raises `ValueError: Unsupported message content type…` on the rest — and a thread deliberately survives a `/model` switch, so the checkpoint replays the previous provider's `thinking`/`reasoning`/`tool_result` blocks on **every** turn: the thread is bricked, not merely failing once. Olano's own attachment composer (`runtime/api.py:_compose_message_with_attachments`) emits Anthropic-shaped `{"type": "image", "source": {…}}`, which is in the same rejected set. The subclass sanitizes at `_convert_messages_to_ollama_messages` — the single choke point `_chat_params` calls, so one override covers all four entry points — dropping reasoning (ollama takes none back on the wire), translating Anthropic images to `base64`/`mime_type`, degrading the rest to text, and passing supported blocks through **by identity** so a normal turn allocates nothing. Don't "simplify" it back to `ChatOllama(...)`.

### Tool resolution is lazy — keep it that way

`resolve_tools(names)` resolves each name through the **generated static index** (`olano/tools/_name_index.py`) and imports only the owning toolkit module. The fallback full scan (`registry._ensure_index`: import all ~75 toolkits, build ~650 langchain tools, ~2.5s) must stay off the agent-build path — it's for `list_tool_names()` (dashboard/catalog, warmed off-path by `server`). After adding/renaming a tool or toolkit, regenerate the index with `uv run python scripts/gen_tool_name_index.py`; `tests/test_tool_name_index.py` fails when it's stale. Same discipline for per-turn contextvars: `AGENT_CTX` lives in `tools/_agent_ctx.py` precisely so binding it per turn doesn't import `google_tools` (~0.35s).

### Profiling response performance

`uv run python scripts/bench_agent_turn.py --agent test-agent-fake --turns 5` measures import/build (with the boot_profile tree) and per-turn time-to-first-token + totals; `--agent test-agent-openai` for real end-to-end numbers, `--cprofile out.pstats` for the turn loop. Reference (this container, warm): fake build ~1.8s, warm turn overhead ~80ms.

### Profiling memory — the fixed floor, not the agents

`uv run python scripts/bench_agent_memory.py --agents 3 --turns 3 --concurrent` reports RSS at every boundary (imports → per-agent build → idle → turn peak → retained), in a throwaway home, on the `fake:` model so the numbers are olano's own allocation. `--attribute-imports` charges RSS growth to the package that triggered the import (this is how you find a provider SDK being imported eagerly); `--archetype agentfather` profiles a real heavyweight; `--mcp-local N` attaches the keyless stdio server in `scripts/bench_mcp_server.py`; `--seed-docs N` gives RAG something real to ingest.

**The number to watch is the baseline, not the per-agent cost.** Measured (this container): 112 MB imports, **+62 MB on the first agent build**, **+1.3 MB on every agent after it**. That first-build cost is lazy process-wide infrastructure, and it used to be +141 MB: deepagents imports `langchain_openai` at module level purely to keep its chat classes in two constants (`middleware/unsupported_content._OPENAI_FILE_MODEL_TYPES`, `middleware/_skill_tools._CHAT_OPENAI_TYPE`; through 0.7.11 it was `langchain_google_genai` too, for one `isinstance` tuple in `filesystem.py`), and tries `langchain_aws` / `langchain_fireworks` on every `create_deep_agent` for middleware that no-ops on every other provider, so every build paid ~60 MB for SDKs its model never used. `builder._ensure_deepagents_provider_imports_deferred` masks `langchain_openai` in `sys.modules` for the one deepagents import (the guarded imports take their `ImportError` branch, the entry is removed at once, a later genuine import proceeds), wraps the two functions that read the emptied constants so they fill them from `sys.modules` first (`_fill_deferred_openai_types`; deepagents' own predicates then decide, `isinstance` in one and exact type in the other), and gates the Bedrock and Fireworks factories on their package being loaded. It must run before anything else imports deepagents on a cold process, which is why `_build_prelude` calls it first. **A missing patch target logs a warning and fails `test_every_patch_target_still_exists`**: assigning to a module attribute that no longer exists succeeds, which is how the 0.7.11 predicate swap kept "applying" on 0.7.23 while OpenAI Responses models silently lost `.docx` pass-through and inline skill-tool disclosure. `web_search` (tavily → cohere + tokenizers) imports inside the function for the same reason; `web_search.TavilyClient` stays a module attribute because tests patch it. `tests/test_provider_import_deferral.py` pins all of it in a subprocess — the only honest test of a first-import-wins mechanism. `anthropic` (17 MB) stays: unguarded upstream. A turn peaks +7 MB on its first run per agent and +0.2 MB thereafter, and three agents answering at once peak +0.2 MB *total* — so density is a floor problem, never an agent-count problem.

**The other floor is the embedding arena, and it is set by batch size, not by how much you ingest.** onnxruntime keeps its high-water mark for the life of the process, and that mark scales ~linearly with `LIONCLAW_EMBEDDING_BATCH_SIZE` (~32 MB per unit at 1500-char chunks): the real `USER_GUIDE.md` every workspace carries (234 chunks) through the real path (`RAGMemory.ingest_file → Chroma → encoder`) cost **+577 MB at batch 16 and +95 MB at batch 1** — and the smaller batch is *faster* (137 s → 80 s), because the default single encoder thread has no parallelism for a wider batch to amortize. The default is **1** now; a 3-agent RAG fleet went 968 → 447 MB. The previous sweep measured 16/32/64, saw the curve and stopped at 16 as "conservative" without looking below. Two harness lessons from finding this: the ingest reads `config.workspace`, **not** `backend.root_dir`, so a synthetic config that sets only the latter ingests an empty default and shows a null result for any batch size — and a null result from a memory harness deserves the same suspicion as a positive one. Full before/after tables, the remote-vs-stdio MCP measurements and the caveats: `agent_memory_profile.md` in the internal engineering notes (private `olano-ai/cloud` repo, `docs/olano-dev/knowledge/`).

Two traps that make a naive measurement wrong. **`malloc_trim` before every reading** — glibc holds freed arenas, so RSS after a turn overstates what is live, and the distinction decides whether a fix belongs in olano or in allocator tuning (`settle()` does both). And **a stdio MCP server's cost is not in this process**: olano closes the session after tool discovery, so an idle agent holds zero either way, but a *call* on a stdio server spawns a fresh interpreter — measured **+58.5 MB in a child** against **+5.2 MB and no child** for the same call on a remote HTTP server (live `search.parallel.ai`), so `--mcp-local` is 11× `--mcp` on the one axis a constrained box cares about, and only `child_rss_total()`'s `/proc` walk can see it. Attaching either leaves the per-agent marginal flat (1.7 MB with Parallel on every agent).

`uv run python scripts/bench_home_config.py` sweeps a dashboard page load against a throwaway home and reports **how many times `config.yaml` was parsed per request**, attributed to the calling function. The number to watch is that parse count, not the milliseconds: every `load_*_settings()` goes through the cached `home.read_home_config_doc()`, so a healthy tree reads **0.0 parses per request** and a new uncached reader shows up as a jump long before anyone notices latency — the report then names it. `--compare` re-runs with the cache defeated (isolates the caching half only; the loader is libyaml either way). This exists because one `GET /api/agents/{name}` used to parse that file 22×.

## Key modules

| Module | Role |
|--------|------|
| `olano/core/builder.py` | `build_agent()` — wires model + backend + tools + skills + checkpointer into a `create_deep_agent` call. Per-agent `config.env` is **not** flattened into global `os.environ` (that would collide across agents); it's applied transiently around the model build (`_transient_env`) and bound per-turn as a credential overlay instead. **`build_agent_async` runs its blocking phases off the event loop** (`_build_prelude` → `_prepare_agent_build_rest` → `_create_agent_graph`, each via `asyncio.to_thread`) so uvicorn keeps answering `/api/status` while agents boot — cold-build loop stall ~3.2s → ~0.15s. The one exception is the `_transient_env` model build: those provider keys are process-global, so the window is only safe with nothing else running (true on the loop, false in a thread) and it stays inline — ~1ms, since `_build_prelude` warms the provider import first. Agents with no overlay skip the window entirely. `_BUILD_LOCK` (reentrant) serializes the sync phases now that two builds can genuinely overlap, and guards the one-shot deepagents patches. |
| `olano/core/runner.py` | `AgentRunner` — streaming, `astream_events()`, JSONL session persistence. Automatic context bounding is delegated to deepagents' `SummarizationMiddleware` (there is **no** olano-side `maybe_summarize` anymore — removed in `d170763`); `astream_events()` drops that middleware's own summary output (chunks whose stream metadata carries `lc_source="summarization"`, via `_is_internal_chunk`, which also drops anything tagged `nostream`) so neither the compaction template nor an in-graph tool's model call ever leaks into a reply. Both `astream_events()` and `ainvoke()` bind the agent's identity + credential overlay for the turn (`agent_runtime_context`). **`ainvoke()` is a thin wrapper over `astream_events()`**, exactly as `astream()` is: it collects the `text` events and returns `""` on a `message_policy` decline. It used to drive the graph itself and persisted only a `user` and an `assistant` row, so every non-streaming caller (the scheduler and its heartbeat, issue and Gmail polls, webhooks, REST `/api/chat`, inbound MCP/A2A, `talk_to_agent` peers, the onboarding greeting) left a thread that showed the prompt and the final answer and nothing in between, while the identical turn typed into chat recorded every tool call, tool result and `write_todos` step. The peer-specific rows (`peer_inbound` / `via_peer`, read off `RequestContext.source == "peer"`) and the transient `a2a_preamble` system message now live inside the stream path, so a fake graph in a test must provide `astream`; a bare `ainvoke` mock is never called except by the stream's own no-text fallback. `ainvoke(override_model=, override_reasoning_effort=)` forwards the chat chips' two per-turn overrides, which is how a scheduled job's `model` / `reasoning_effort` (a `tasks` row column pair or `ScheduleConfig` fields, validated at every write by `admin.scheduler.validate_task_model` (provider connected) and `validate_task_effort` (over `scheduler/overrides.py`, against the ladder of the model the job runs on: its own, else the agent's, checked as the pair will be after the edit)) reach the turn. **Effort ladders come from `models/reasoning._probe`, package profile first, synced catalog second**: the installed integration package's model profile is authoritative when it lists levels, and the catalog entry's `reasoningEfforts` / `reasoningDefault` answer only when the package is silent (langchain-openai 1.7.0 ships a `gpt-6.1-sol` profile with no levels, which hid the chip and dropped every effort for that model). The package half is memoized, the catalog half is a dict hit so a sync is visible without a restart, and the chat chip, agent-level resolution and the kwarg gate all read that one probe, so no surface can offer a level another drops. **Text resuming after a tool boundary gets a `"\n\n"` chunk first** (`_take_text` / `_needs_paragraph_break`) — every consumer concatenates chunks verbatim, so without it "…are drawn." and "Found it —" read as one sentence — and the turn is recorded as ordered `segments` `[{text, after: <tool_call_id>}]`, persisted on the assistant JSONL row only when the turn actually interleaved (single-segment rows stay byte-identical) so the dashboard can put tool cards between the paragraphs they belong to. |
| `olano/core/mcp_result_cap_middleware.py` + `config/system_settings.py:ContextWindowSettings` | **The conversation is bounded by policy, never by deepagents' fallbacks.** deepagents sizes compaction from `model.profile["max_input_tokens"]`, a static table in each provider's pip package, so a model the package predates (`openai-codex:gpt-6-luna`) got its no-profile fallback: **keep the last 6 messages**, and an agent forgot the start of a five-message session. `models.attach_context_profile` (every `build_model`) hands the catalog window to a client with none; `effective_context_window()` resolves `config.yaml → context_window` + `agent.json5 → context_window` (agent wins, same clamps, keep strictly below trigger) into fractions when the window is known and absolute tokens otherwise, never a message count; `builder._make_summarization_middleware` builds every `SummarizationMiddleware` under it, via the `create_summarization_middleware` wrapper reading `_ACTIVE_CONTEXT_POLICY`, a contextvar `_create_agent_graph` binds around `create_deep_agent` (subagents' middlewares are built inside that call). The `compact_conversation` tool takes the same engine: it shares `_summarization_event` with the automatic one. Two offloads were silently dead on filesystem backends because deepagents' `artifacts_root` is `/`: `_ensure_filesystem_offload_patch` moves `large_tool_results`/`conversation_history` under `<workspace>/.olano/` (never for `StateBackend`/`CompositeBackend`/virtual mode). MCP results had no cap at all; `McpResultCapMiddleware` (wired from the live connect summary's tool names) offloads any over `mcp_result_token_limit` (5k, 0 = off) with plain host I/O + `handoff_to_sandbox`, keeps `[trusted=false]` as the replacement's first line, and keeps the original on a failed write. `/context` charged MCP tools 0 as "on-demand" (they are bound into every request), so their schemas showed up as *Messages*; summary rows now carry `tool_details`/`tool_tokens`/`disabled`, read by `context_report`, `self_list_mcp_tools` and the prompt's MCP block. `/compact` looked like a no-op because the header bar is the last *streamed* turn's `usage.context`; the endpoint now returns the post-compaction estimate (`estimate_thread_context_tokens`, event applied) and the client seeds the bar with it. Every offload lands under `Workspace.state_dir`; the folder name is spelled once, `config/workspace.WORKSPACE_STATE_DIRNAME`, never as a literal, and `adopt_legacy_state_dir` (run by every `Workspace` construction and at scaffold time) moves a pre-rename `.lionclaw/` to `.olano/` once, leaving a relative symlink at the old name so paths recorded in checkpoints and notes keep resolving (`cartography/walker.SKIP_DIR_NAMES` lists both names for the same reason). The agent's own MCP repair loop: `self_list_mcp_servers` merges config with the live connect summary and the stored OAuth token state plus a per-row `fix`, and `self_reload_mcp_servers` reconnects through `RuntimeServer.reload_agent_mcp` via `talk_to.get_bound_runtime()`; a reload never invents consent, an `auth_required` row still points at `self_authorize_mcp_server`. |
| `olano/runtime/media_refs.py` | **Files named in chat become inline media or cards.** `detect_media_refs(text, root, agent)` resolves every path-like token (absolute, workspace-relative, backticked, `file://`, `/workspace/…`) to an existing regular file inside the agent's workspace and returns `{kind, name, path, mime, url, size, files_url, download_url, mentions}`; image/audio/video render inline, `document`/`file` render as a card (Download = `/api/files-raw/…&download=1`, Open in Files = `/files?path=…&agent=…`). **Only the finished message hands a file over** (`SCAN_TOOL_RESULTS = False`): it runs on the **assistant's own reply** (accumulated by `/api/chat/stream`, one `{"type": "media"}` frame before `done`) and on `assistant`/`user`/`peer_inbound` rows in `api._transcript_message` on reload — never on `tool_result`. It used to scan every tool result, and the client folds a tool result's media into the *assistant message*, so any path an intermediate tool's output merely mentioned became a card under the answer: a `read_file` returns the file's contents, so a document citing `system/knowledge/USER_GUIDE.md` attached the 257 KB user guide to an answer about something else. ## Checkpoint history: a step's write is a delta, and the history is swept

deepagents stores `messages` (and `files`) as a LangGraph **`DeltaChannel`**
(`snapshot_frequency=50`): a full snapshot blob every 50 updates, and between
snapshots only each step's write. Loading a thread is the latest checkpoint plus
**every `messages` write since the last snapshot, replayed**
(`AsyncPostgresSaver.aget_delta_channel_history`, a parent-chain walk back to
each channel's *seed*: the newest ancestor holding a blob or an inline value).
Two consequences shape three pieces of code.

- **A middleware hook's return value is that step's write.** The security
  middleware (`security/deepagents_middleware.py`) returned the whole message
  list whenever its PII scan, credential scrub or a hook rewrote one message;
  the reducer merged it by id, so the state was right, but on a long thread
  every model step wrote the entire conversation (42 MB per step on one managed
  box's peer thread, 40 GB of `checkpoint_writes`), and every load replayed up
  to 50 of those: 3 to 8 GB per turn, the runtime OOM-killed at its cgroup cap
  and "the deployment is not responding" in every client. The hooks now return
  only the message they rewrote (`_replacement_update`; the full list only for a
  message with no id, which LangGraph never persists). Any new hook that touches
  `messages` follows the same rule, pinned by
  `tests/test_security_middleware_write_size.py`.
- **Nothing in LangGraph deletes a checkpoint.** `core/checkpoint_gc.py` keeps,
  per `(thread, namespace)`, the chain from the latest checkpoint back to the
  oldest delta-channel seed (a channel with no seed keeps back to its oldest
  write), always at least `keep_min`, and removes older checkpoints and writes
  plus the blobs no surviving checkpoint names (blobs are keyed by version, so
  the sweep is by reference, never by age). The runtime runs it
  `boot_delay_minutes` after boot and every `interval_hours`
  (`config.yaml → checkpoint_gc`, `LIONCLAW_NO_CHECKPOINT_GC=1` for one boot),
  admins at `GET|POST /api/diagnostics/checkpoints[/gc]`. Postgres only; the
  sqlite saver has its own delta layout and is untouched. The honest test is
  `tests/test_checkpoint_gc.py` against a real Postgres: a real graph with the
  delta reducer, a whole-list-rewriting node and sub-namespaces, swept, and the
  reconstructed state compared byte for byte. The seed may be the tip itself:
  a checkpoint holding the channel's value is restored from it (the loader
  walks only for a channel with nothing stored, `_delta_channels_to_replay`),
  and the next step's walk starts at its parent, which is the tip.
  **A channel that never snapshotted pins the whole chain, and the sweep
  writes the snapshot itself.** `files` snapshots every 50 file updates or
  5000 steps, so a conversation that touched a file once early on never gets
  one, its oldest `files` write is the cut, and nothing above it can go; the
  retired generations of agent-to-agent threads never step again, so they
  would hold their history forever (one managed box: 8,257 checkpoints and 4 GB of
  writes on one thread a day after its last step, five sweeps that removed
  nothing). With the saver (`checkpoints.aget_postgres_saver`),
  `collect` compacts: a seedless channel, or a seeded one whose writes since
  the seed outweigh `resnapshot_bytes` (8 MB, the replay a thread that never
  steps again would pay on every load), is rebuilt the way a load rebuilds
  it but **one stored write at a time** (`_materialize`: the seed's blob, then
  each write through the channel's own `replay_writes`; reducers are
  batching-invariant by contract), so a 700 MB replay of whole-conversation
  writes costs the running value plus one write, never the history; then one
  checkpoint carrying a `_DeltaSnapshot` goes on the tip through
  `saver.aput` (what the pregel loop writes at a snapshot step, minus the
  step) and the sweep cuts behind it. **The publish is serialized against
  the writers** (`core/thread_locks.py`): the saver orders single operations,
  not the compactor's rebuild-then-publish, so a turn that resumed the thread
  between the guards and the publish used to be rolled back (its checkpoint
  sat under the compactor's newer-id row carrying the pre-turn versions;
  reproduced on a real Postgres by the review of #682). Now the runner holds
  one lock per checkpoint thread id for the whole turn (`astream_events`,
  under the agent-scoped id) and so does `cognition.worker.run_worker`
  (under its `cog::` id); the compactor rebuilds unlocked, then
  `try_acquire`s, re-reads the tip and the pending writes under the lock,
  publishes and releases within milliseconds, and skips the namespace when
  a turn holds it or the tip moved. The quiet window (`quiet_seconds`,
  30 min) and the pending-write check stay as the belt for a writer outside
  this process (a one-shot CLI run against a live server's database), which
  the lock cannot see. `channel_specs` come off deepagents' own state
  annotations (`default_channel_specs`), so the reducer and cadence are the
  running graph's. `tests/test_checkpoint_gc.py` drives both shapes on a
  real Postgres, compares the reconstructed state before and after, and
  replays the review's race (a turn completing inside the rebuild) expecting
  the turn to survive; `tests/test_thread_locks.py` pins the hand-off and
  that the runner holds the lock for the turn.
  **Deleting an agent deletes its history too** (`checkpoints.delete_agent_threads`,
  from both the admin function and the dashboard route): every thread under
  the agent's `<name>::` prefix **and its background runs**, which a
  cognition worker or `delegate_task` child writes under a raw
  `cog::<parent>__cog__<label>__<hex>` id (`__sub__` for a delegate) that
  never carries the parent's prefix. `checkpoints.thread_owner` is the one
  definition of whose thread an id is; it used to leave the rows as
  "harmless" orphans, and on one managed box those were the largest rows in the store.
  The sweep reports `orphan_namespaces` for threads whose owner is no live
  agent and deletes none of them (reading `cog` as an agent name counted
  every background run of every live agent as an orphan). A box upgraded from the whole-list release still
  replays its old large writes until each thread's next snapshot, so migration
  `0029_checkpoint_history_resnapshot` arms every root thread with 5+ pending
  `messages` writes by setting `counters_since_delta_snapshot.messages` past
  any `snapshot_frequency` in the latest checkpoint's metadata (what the pregel
  loop reads back): the next update writes a snapshot, and the sweep ten minutes
  after that boot takes the rest. Nothing on the box has to be run by hand.
- **A peer thread rolls over.** `talk_to.py:_pair_thread_id` resumed
  `acp::<caller>::<callee>` forever (20,078 checkpoints on one pair);
  `_peer_thread_id` now moves to `acp::<caller>::<callee>::<stamp>` once the
  callee's transcript holds `peer_threads.max_turns` rows (200) or is older
  than `peer_threads.max_age_days` (3), measured off the JSONL with a stat-keyed
  cache (rows and first timestamp cached per file; the bounds apply at call
  time, so `config.yaml → peer_threads`, edited from Config → Agent-to-agent
  conversations, takes effect on the next call with no restart;
  `rotate: false` keeps the one thread forever). The prefix and the pair stay
  in the id, which is all any consumer parses (`_is_user_thread`,
  `thread_labels`, the A2A view keys on from/to). Both this block and
  `checkpoint_gc` are patchable through `admin/config._SECTION_WRITERS`
  (`olano_update_home_config`) and `PUT /api/system/config`.

The per-turn checkpoint loads are not the lever: the streaming path loads the
thread once (plus once more only when a tool approval is pending or on a
resume); `_billed_message_ids` and `estimate_thread_context_tokens` serve the
no-text fallback and `/compact`. What a turn costs is the write size and the
replay depth above.

**The other reader of whole threads is the Insights cost miner, and it runs on
dashboard requests, not on turns.** `analytics/threadcost/service.warm_cache`
(behind every `/api/analytics/threadcost/*` route, and behind
`/api/analytics/overview` only when the window reaches back before the usage
ledger's first day, so the Overview page's 30-day teaser mines nothing on a box
whose ledger is older than that) re-mines each thread whose version moved by
loading its full state through a sync `PostgresSaver`, up to 150 per request,
inline in the request's worker thread; `thread_calls` does the same for one
thread on every thread open, from the dashboard and the mobile app alike. The
same two reader functions serve the raw-call inspector (`call_raw`), the
Insights tools card (`tools_rollup`), the health page's probe (`diagnostics`)
and the boot-time credits backfill's replay (`backfill._replay_thread_credits`),
and every one of them asks `history_too_large` first: a cap on the warmer alone
leaves a drill-down click as the one request that loads the thread everything
else refused. On the box above, 0.10.5 cleaned the
stored history and the kills went on: three climbs from under 1 GB to 12 GB in
5 to 7 minutes with no inbound message anywhere near them, because the heavy
peer threads had not turned yet (nothing re-snapshotted them) and a page load
read them whole. Three bounds now hold, all in `service.py`: a thread whose
pending `messages` history (`reader.pending_history_bytes`, the writes from
the channel's seed onwards plus the seed blob, bytes only, Postgres only; *from*
the seed because the saver's chain walk replays the step written on top of the
snapshot too) is over
`LIONCLAW_THREADCOST_MAX_HISTORY_MB` (64) is not read and not retried until
its version moves; one warm pass runs at a time per process (a concurrent
request serves the cache); and staleness compares the newest checkpoint id
only (`reader.version_key`), never the row count, because the sweep changes
the count of every thread it trims and used to mark them all stale at once.
A too-large thread shows "—" in Insights until its next turn snapshots it and
the sweep drops the old writes, which brings it under the cap by itself (or
the sweep's compaction does, for a thread that never turns again). The pass
itself is bounded too: 40 threads per request, not 150, and `_release_heap`
after every pass that read anything. Every thread the warmer reads is
deserialized whole and freed, and glibc keeps freed arenas mapped, so on
core each Insights load left RSS a gigabyte higher (270 MB traced behind
4.6 GB of RSS) and the sampler read it as a leak. That gap is consistent
with retained freed heap and was reproduced locally, but RSS minus traced
bytes does not *prove* it: native allocations tracemalloc never sees,
tracing's own bookkeeping and allocations made before tracing began all
land there too, which is what the `allocator` block of
`GET /api/diagnostics/memory` (`admin/memory.glibc_allocator`, `mallinfo2`)
is for: `free_mb` says retention, `allocated_mb` says the memory has an
owner and attribution still needs a native profiler. `malloc_trim` and
`MALLOC_ARENA_MAX=2` address retention only; neither bounds live memory.
Note also that the sweep's deletions make Postgres space reusable inside
the relation; the 40 GB `checkpoint_writes` file shrinks only with a
`VACUUM FULL` or a rewrite, so judge the sweep by live rows, not by the
relation size.

## Sessions (JSONL)

Stored at `~/.olano/sessions/<agent>/<thread_id>.jsonl`. ## CI runs the suite in parallel

CI runs `pytest -n auto --dist loadfile` (pytest-xdist, already in the `dev`
group) under `timeout-minutes: 25`. Run serially under the old 15-minute limit
the suite sat right on the wall, so which side of it a run landed on was runner
variance — `main` was cancelled mid-suite roughly half the time with **nothing
failing**. A red check that means nothing is worse than no check: the next real
failure gets read as "the usual timeout".

Both halves of that fix are load-bearing, and the measurements say why. On the
`Run tests` step alone:

| | serial | parallel |
|---|---|---|
| CI, fast runner | 10m06s | **9m07s** |
| CI, slow runner | >14m45s (killed at 99%) | — |
| local, 4 cores | 946s | **266s** (3.6×) |

The 3.6× is a 4-core box; a GitHub runner has fewer, so against the *fast*
serial run parallelism bought about a minute (1.11×). The dominant term is not
the suite's length but the ~50% spread between runners — the same commit ran
10m06s and >14m45s. Parallelism cannot compress that spread; only headroom can.
So the timeout carries the variance and the parallelism carries the duration,
and removing either one brings the coin flip back.

Two things this asks of test code:

- **A `parametrize` value must be identical in every process.** xdist compares
  the workers' collections and refuses to run when they disagree (`Different
  tests were collected between gw0 and gw1`). Anything computed at *collection*
  time — `uuid.uuid4()`, `random`, a timestamp — puts a different test id in
  each worker. It is worth avoiding even serially: a moving id means `--lf`,
  `--deselect` and any per-test history can never name the case.
  `test_checkpoints.py::TestScopeThread::test_roundtrip` was the one instance.
- **`--dist loadfile` keeps a file's tests on one worker**, so module-scoped
  fixtures and within-file ordering behave exactly as they do serially, and
  assignment is deterministic instead of reshuffled per run. Tests still must
  not depend on *another file* having run first.

Parallelism is safe here because the autouse `lionclaw_home` fixture gives every
test its own tmp home — workers share no state. Locally `uv run pytest tests/ -q`
stays serial, which is easier to debug; add `-n auto` when you want the speed.

### Coverage runs on `sys.monitoring`, not the C tracer

The coverage run (post-merge only — PRs run plain pytest) sets
**`COVERAGE_CORE=sysmon`**. coverage.py's default core calls back into Python on
every line; since 3.12 it can drive `sys.monitoring` instead, where the
interpreter simply does not instrument what it is not asked about. Measured at
the shape CI runs (`-n 4 --dist loadfile`, 3.13.7, 24-file subset): **16.0s
uninstrumented, 19.5s default core (+21.9%), 16.2s sysmon (+1.3%)** — and
**byte-identical** results on both cores (110981 statements / 89221 missed / 20%,
serial and under xdist). It is not trading measurement for speed. On CI the
coverage step was 14m35s against 9m28s for the same suite without it, so ~5
minutes of every post-merge run was tracer overhead.

If the matrix ever gains an interpreter without `sys.monitoring`, coverage emits
a `no-sysmon` warning, falls back to the default core and still passes (verified
on 3.11.15) — it degrades to slow, never to wrong.

Two related things worth knowing before "optimizing" CI further. The **test job
is ~80% of the bill and is one runner** — `-n auto` gets a standard runner's 4
cores and no more; sharding across N runners cuts wall clock ~N-fold and *raises*
the billed total, so it is a money-for-latency trade rather than a win. And a
merged PR pays for **two** runs of `ci.yml` (the PR run and the post-merge push
run), ~31 billed minutes per feature; `ci.yml`'s header carries the measured
per-job breakdown.

## Images: `:edge` is `main`, `:latest` is a release

`build-images.yml` builds `main` every 3 hours into `:edge` plus `:<sha>`, and
only from a commit whose workflow runs are all green
(`.github/scripts/checks-green.sh`; a commit with no runs counts as green,
because `ci.yml` ignores docs-only commits). It never touches `:latest`.
A pending verdict skips the scheduled window, but a **dispatch** waits for
the running checks (`CHECKS_WAIT_SECONDS`, 75 minutes: e2e.yml's job timeout)
and so does the release gate; failing at once only sent the person to
`force=true`, which publishes an image nothing has tested.
`release.yml` runs on a `vX.Y.Z` tag, or on a dispatch that names the version
and creates that tag itself once the gate has passed (an agent session can
dispatch a workflow but cannot push a tag), and **promotes** that commit's
existing `:<sha>` image to `:X.Y.Z`, `:X.Y` and `:latest` by re-tagging
(building only when no edge build has published it), so the image the fleet
gets is the one the canaries ran. Both workflows build through the one definition in
`.github/actions/build-images`. Managed deployments and fresh provisioning
pull `:latest`, which is why a merge to `main` cannot reach a customer on its
own.

Three things the scheme depends on. The tag's version must equal
`pyproject.toml`'s (bump it in a PR and run `uv lock`, or the release refuses
the tag). A pre-release tag (any hyphen) moves neither `:latest` nor `:X.Y`.
And the cloud's image-freshness alarm must watch `:edge`, not `:latest`: by
design `:latest` now sits still between releases, and an alarm that compares
it with `main`'s tip would page forever. `tests/test_release_pipeline.py` pins
the workflow shape and runs the gate script against saved API shapes for every
verdict. The procedure, hotfixes and rollback: `docs/RELEASING.md`.

## Sandbox backend: verify against a real container

`OlanoDockerBackend` subclasses deepagents' `BaseSandbox`, so deepagents
implements every file operation (`ls`/`als`/`read`/`write`/`edit`/`glob`/`grep`/
`delete`) on top of the three primitives the backend supplies — `execute()`,
`upload_files()`, `download_files()` — plus an `id` property. **Don't hand-roll
the file operations**: deepagents runs server-side `python3` scripts and parses
their JSON into `LsResult`/`ReadResult`/… dataclasses, and a class that only
looks like a backend satisfies none of that (it also loses the `execute` tool,
which is gated on `isinstance(backend, SandboxBackendProtocol)`).

### Docker in an agent session: installed, not running

**A Claude Code / agent session has docker available, and one `docker info` will
tell you it does not.** The binaries are installed (`/usr/bin/dockerd`) but no
daemon runs and no socket exists, so the first probe answers *"Cannot connect to
the Docker daemon"* — which reads exactly like "this environment has no docker",
and on that reading `make test-sandbox`, everything under `tests/integration/`
and the whole sandbox egress lane get written off as unverifiable in an
environment where they run fine. **One failed socket check is not a capability
check.** `.claude/session-start.sh` now starts the daemon on every session, so
normally it is already up; when it is not, start it and re-probe before
concluding anything:

```bash
( nohup dockerd >/tmp/dockerd.log 2>&1 & ) ; sleep 8 ; docker info
```

`.gitignore` ignores `.claude/*` and negates that hook and `settings.json`
explicitly — a hook that exists only inside one container dies with it, which is
the same as not having one, so don't "tidy" those two negations away.

Three things make that fail in ways worth recognising:

- **A stale `/var/run/docker.pid`.** A recycled session leaves the pidfile
  behind with a PID something unrelated has since been assigned, and dockerd
  refuses: *"ensure docker is not running or delete /var/run/docker.pid:
  process with PID N is still running"*. Delete it **only** when
  `pgrep -x dockerd` finds nothing, so a genuinely running daemon is never
  disturbed — that is what the hook does.
- **Docker Hub half works, which is worse than not working.** The registry API
  answers (`registry-1.docker.io/v2/` → 401, the normal auth challenge) but the
  agent proxy denies CONNECT to `production.cloudfront.docker.com`, so a pull
  authenticates, resolves the manifest and *then* dies `Forbidden` on whichever
  layers that CDN serves. Which ones those are varies by image — measured the
  same minute, `docker pull busybox:1.36` succeeded and
  `docker pull debian:bookworm-slim` failed on its first blob — so one
  successful Hub pull proves nothing about the next. **`mirror.gcr.io` and
  `public.ecr.aws` both work reliably** — `docker pull
  mirror.gcr.io/library/alpine:3.20 && docker tag
  mirror.gcr.io/library/alpine:3.20 alpine:3.20` is the standing recipe, and
  `tests/integration/test_sandbox_egress_live.py` takes
  `LIONCLAW_EGRESS_TEST_IMAGE` for exactly this. `ghcr.io` is reachable but
  `ghcr.io/olano-ai/olano-sandbox` is private, so `make test-sandbox` proper
  still needs a credential; the live tests that only need *a* container do not.
- **`/var/lib/docker` survives** a daemon stop and (in practice) a session
  recycle, so images pulled earlier are often still there — check
  `docker images` before pulling anything.

The kernel side works too: `iptables` is present and `DOCKER-USER` is
insertable as root, which is what makes the sandbox egress firewall testable
here (`tests/integration/test_sandbox_egress_live.py`).

Anything touching the container boundary must be checked with
`make test-sandbox` (`tests/integration/test_sandbox_live.py`) — the unit suite
fakes the `docker exec` hop and is blind to whatever the kernel decides.
Bugs that only appear there: a login shell printing its profile into the JSON
deepagents parses (hence `sh -c`, not `sh -lc`), a workspace the runtime seeded
as root that the uid-1000 agent can't write (hence
`_ensure_sandbox_shared_dir(ws, recursive=True)`), and 0600 files the agent is
told to read but can't open (hence `builder.chown_for_sandbox`).

CI runs the same suite (`.github/workflows/sandbox-live.yml`, as root, against
the published sandbox image) on pull requests that touch `olano/backends/`, the
egress firewall, `docker/olano-sandbox/` or `tests/integration/`, and on demand
from the Actions tab for any branch. A skip for a missing prerequisite (no
Docker, no image, no iptables) fails that job instead of reading as green.

Note `execute()` returns stdout+stderr merged per the deepagents protocol;
Olano callers that need them apart use the backend's own `run()`.

**The image carries the document toolchain, and existing containers reach it
only through a signature bump.** LibreOffice, `tesseract` (`eng`+`osd`),
ImageMagick, `qpdf` and the Liberation 2 + Noto core fonts are baked in by
default — `SANDBOX_EXTRAS` is an opt-**out** now (`=0` builds the lean image) —
and `install.sh` puts the same tools on the host lane (`--no-office` declines;
macOS needs an explicit `--office`). `_container_signature` hashes the image
**tag**, never a digest, so re-pulling never recreates a running container:
baked content reaches existing boxes only when `"schema"` moves (3 → 4 here).
Three things in that layer are load-bearing: the language data are apt
*Recommends* under `--no-install-recommends` so `tesseract-ocr-eng`/`-osd` are
named explicitly, LibreOffice ships no fonts of its own, and the first `soffice`
run builds a user profile (pre-built at build time as uid 1000, because 15-40 s
on a 0.5-CPU sandbox loses to a 60 s exec timeout). ImageMagick cannot read or write PDF/PS/EPS by distribution
policy, and that stays; `pdftk` is absent on purpose (a JRE for a subset of
qpdf). The skill fonts ride the existing tool-layer mount
(`interpreter_shims.ensure_skill_fonts` → `/opt/agent-tools/fonts`, registered by
a fontconfig fragment) and needed no bump.

**The document skills are not in this repository.** `docx`, `pdf`, `pptx` and
`xlsx` are Olano-authored under a proprietary license, so they live only in the
private `olano-ai/skills` catalog and reach managed boxes through the cloud
skills catalog; a self-hosted install has the toolchain above and not those
skills. Never bundle them back into `olano/skills/built_in/` (it ships in the
public wheel and images): `tests/test_retired_document_skills.py` fails on any
built-in skill whose license forbids redistribution. Until 0.3.1 the package
bundled Anthropic's proprietary versions under the same names, and a box that
synced them keeps them until something removes them: the built-in removal pass
takes the package's copies, `skills/sync._copy_pack_skills` refuses to install
one from a stale pack on disk, and the startup-upgrade hook runs
`retire_proprietary_skill_copies` once per release. All three match by name
**and** license (`built_in_sync.is_retired_proprietary_copy`) and touch only
sync-managed, unpinned copies, so an operator's own `pdf` skill survives.

**Every runtime write into a workspace is handed to the agent.** The sandbox
agent is uid/gid 1000 and a bind mount preserves host ownership, so a chart the
runtime rendered is one the agent can read and cannot overwrite. A write that
goes through `markdown_memory.atomic_write_text` needs nothing more: it calls
`_sandbox_exec.handoff_workspace_write`, which finds the live sandbox whose
workspace holds the path (no agent name, no contextvar) and re-owns the file and
every directory the write created, so MEMORY.md, the daily logs, CORTEX.md and
the activity log belong to the agent by construction. It also keeps the target's
mode across the rename: mkstemp stages at 0600 and the rename used to carry that
onto MEMORY.md, taking the file away from the agent on every `memory_save`. Any
other writer (`open().write`, `shutil`, a library saving a PNG) still calls
`_sandbox_exec.handoff_to_sandbox(path, created=…, agent=…)` after the write —
`missing_parents()` **before** the `mkdir` collects `created`. Two traps: the
gate is a **live sandbox**, not the posture (a *sidecar* counts, so never ask
`sandbox_is_backend`), and the default reads the turn's contextvar, which is
**unset in a dashboard request handler** — those surfaces pass `agent=` by name
or the hand-off silently no-ops exactly where the Files view writes.
`builder.chown_for_sandbox` stays the single `os.chown` in the tree.

**An in-process tool that shells out never reaches the runtime host on a managed
box.** `tools/_sandbox_exec.sandboxed_run` is the one seam: the agent's live
sandbox (a sidecar counts) when there is one, the host only under the open
posture, and otherwise a refusal shaped like a failed command (`returncode ==
EXIT_REFUSED`, stderr `HOST_EXECUTION_REFUSED`, `host_execution_refused(result)`
to tell the two apart) so every subprocess-shaped caller keeps working. The
`safe_shell` / `node_run` / `npm_install` tool bodies go through it (they used to
call `subprocess.run` in the runtime container directly, gated on a feature flag
that failed open), as does `video_to_text`'s ffmpeg. In an agent turn the
security middleware intercepts those tools **by name** before the body runs
(`deepagents_middleware._run_shell_command`, already fail-closed), so the body is
the belt for callers outside the graph; `tests/test_shell_tools_managed_posture.py`
pins both gates and that `_SHELL_TOOL_NAMES` lists every tool `shell.py` and
`node.py` export. A new tool that spawns a process takes `sandboxed_run`, never a
bare `subprocess.run`. `tests/integration/test_sandbox_tooling_live.py` runs the
real paths (middleware lane, tool bodies, `pip install`, `npm install -g`) against
a container under a managed posture.

**A matching signature is not proof the container still reaches anything.** The
signature hashes the *recipe*, so a persistent sandbox is re-adopted across
runtime restarts — and a **docker daemon** restart (engine upgrade, a firewall
reload re-installing netfilter rules, live-restore) can leave a running
container's veth no longer plumbed into the bridge. It keeps its `eth0`, its
`resolv.conf` and its default route and reaches nothing: ARP for the gateway
never completes, so every connect ends `EHOSTUNREACH` or times out and DNS is
the loudest casualty. The symptom is every `npx` dying `EAI_AGAIN` after 144 s
in one container while an identical sibling is fine, and nothing recreates
the container because nothing changed its recipe. `_start_persistent` now
proves reachability before reusing one (`probe_container_network`: a connect to
the gateway that opens *or* is refused, or the gateway's `/proc/net/arp` entry —
the second signal is what keeps a host firewall that deliberately drops
container→host traffic from reading as a fault) and rebuilds it when stranded,
which re-plumbs the veth. **The probe is a polling loop, not one connect**,
because `/proc/net/arp` shows flag `0x2` for every `NUD_VALID` state — `STALE`
included — so a container stranded while *idle* still carries the gateway's old
MAC and a single 1.5 s connect reads it as healthy while the kernel sits in
`DELAY`; the loop says `ok` the instant anything answers, `stranded` once the
entry is absent/incomplete after a 1.5 s grace, and only in the ambiguous case
waits up to 9.5 s for `DELAY`+`PROBE` to settle a stale entry either way (that
cap is the per-agent boot cost on a box whose firewall drops container→host TCP,
and only there). **A lane is also unusable when docker refuses an endpoint
outright**, and that path must reach the same repair: a Linux bridge holds
`BR_MAX_PORTS` = 1024 interfaces and `br_add_if` then returns `-EXFULL`, so
`failed to create endpoint … adding interface vethX to bridge docker0 failed:
exchange full` is docker0 out of port slots (leaked veths). `docker run` failing
that way used to raise straight out of `_start_persistent`, failing every agent
closed with the repair sitting unused below it; `is_network_creation_failure()`
now routes it into the escalation, while a non-network failure (missing image,
bad mount) still raises exactly where it did. Still stranded on a container
built seconds ago ⇒ the bridge itself is broken ⇒ one move to the other lane —
`bridge` ⇄ a dedicated `olano-sandbox` network, both directions, never against
an operator's pin —
remembered in `<home>/run/sandbox-network` so the next boot computes its
signature there instead of rebuilding every start; a remembered network that has
gone is re-created on resolve, or the lane reverts to `bridge` (the marker must
never become a `docker run` that fails for every agent). `resolve_bridge_network()`
is the one resolver, and the ephemeral stdio-MCP lane reads it too. Two rules
keep the cure cheaper than the disease: **an inconclusive probe counts as
healthy** (a rebuild costs the agent every package it installed), and the
escalation happens **once** — after that the runtime reports (`sandbox_status`
→ `admin.diagnostics`, the Terminal tab) rather than looping (and **raises** when
neither lane yielded a container at all, so the builder still fails closed to a
no-shell filesystem backend instead of registering a dead sandbox), because
`ip_forward=0`, a `DROP` in `DOCKER-USER` or a missing `MASQUERADE` is host-side
and nothing in this process can fix it. `LIONCLAW_SANDBOX_NETWORK=bridge` pins
the old lane, `LIONCLAW_SANDBOX_NETCHECK=0` disables probe and repair.

**No container may open a connection to a sandbox, and docker enforces it.** On
a network with inter-container communication on (docker0 always has it) every
container reaches every other container's IP, so a server one agent ran bound
to all interfaces (Express's `app.listen(PORT)`, Python's `http.server`: most of
them) was reachable from every other agent's sandbox, around the page password.
The default lane is now `olano-sandboxes`, a bridge created on demand with
`com.docker.network.bridge.enable_icc=false` (`ensure_isolated_network`,
`default_lane`), so the daemon drops that traffic in its own rules. It had to be
docker, not `iptables`: a containerized runtime (every managed box) writes
iptables into its own network namespace, which is exactly why the egress
firewall degrades there, while the docker socket it always has. Gateway (egress
proxy, embedded DNS) and NAT egress still work; nothing Olano runs needs a
connection *into* a sandbox (page keeper, browser relay and stdio MCP all cross
over exec pipes). The lanes become `olano-sandboxes` ⇄ `olano-sandbox`, and the
rescue network is created ICC-off too while isolation is on, so a repair keeps
the guarantee; an old `bridge` marker resolves to the isolated lane.
`network_isolated(name)` reads the network's own option (truth about the bridge
in use), feeds `network_report()["isolated"]`, the sandbox status reason and the
page card's listen warning (shown only when the port really is reachable). A
same-named network without the option is refused, not used. A box that cannot
create the network falls back to `bridge`, warns once and reports
`isolated: false`; a failed create is retried at most once a minute.
`LIONCLAW_SANDBOX_ISOLATION=0` (or any `LIONCLAW_SANDBOX_NETWORK` pin) restores the
shared bridge. The lane is in the container signature, so turning it on rebuilds
each persistent sandbox once (tool-layer installs survive). `tests/conftest.py`
pins isolation off for the unit suite (no unit test may create a network on a
developer's daemon); the integration suite runs the real default, and
`tests/integration/test_sandbox_isolation_live.py` proves both the block and,
as a control, that the same probe connects on the shared bridge.

**The bridge fills with the runtime's own throwaway containers, and the runtime
reaps them.** A bridge near its 1024-port limit with no orphaned veths means
docker accounts for every port: not leaked interfaces but hundreds of **live
containers** — and the only family the runtime
creates by the hundred is the `--rm` stdio-MCP session (`mcp_stdio_run_args`,
one `docker run -i` per tool call and per boot connect) plus connected jobs.
Their teardown has a gap: the mcp SDK closes stdin, waits 2 s, SIGTERMs the
docker CLI (which proxies it into the container) and 2 s later SIGKILLs the CLI
— and a SIGKILLed CLI proxies nothing, so on a daemon too busy to deliver the
SIGTERM in time, or with a server that shuts down slowly or ignores EOF, the
container keeps running with nobody attached and `--rm` never fires. One bridge
port each, forever, and the busier the daemon gets the more teardowns miss.
`lionclaw_docker.reap_ephemeral_containers()` is the bound: at boot (a
background task beside the agent boot, never ahead of it — removing a thousand
containers takes minutes) and on every `_mcp_health_loop` tick, any container
carrying `olano.mcp=1` / `olano.job` **older than
`LIONCLAW_EPHEMERAL_CONTAINER_MAX_AGE`** (3 h; a `created` husk gets 10 min) is
`docker rm -f`'d. **Age, never the label alone** — a second olano process on the
same daemon (a dev box running a one-shot `olano -n` beside `olano serve`) keeps its
in-flight session. The report rides `GET /api/diagnostics/mcp` →
`ephemeral_containers`; `LIONCLAW_NO_EPHEMERAL_REAP=1` skips it for a boot. An
agent's persistent sandbox cannot leak this way (found by name, reused), but a
**worker's** did: a cognition / `delegate_task` run builds its graph under a
unique name (`<parent>__cog__<label>__<hex>`) and the sandbox keyed on it was a
new persistent container per run that nothing stopped. A month after the MCP
leak the same box read `docker0=2/1024 … top=br-…:959 SATURATED … mcp=0
sbx=960` on twelve agents: the dedicated `olano-sandbox` network full of
sandboxes, the family the census calls "agent sandboxes", and a console that
summarised docker0 and so reported two ports in use beside a saturated badge.
`builder.sandbox_owner(config)` (`credential_scope or name`, the same seam that
makes a worker resolve credentials as its parent) now decides whose container a
build attaches to: a worker is handed its parent's live backend when the parent
is in the registry, else starts one under the **parent's** name, and
`release_agent_sandbox` drops the child's registry/status rows when the run
ends (`worker._release_sandbox_registration`). The sweep's third family,
`worker`, is `label=lionclaw.signature` + `name=__cog__` / `name=__sub__`:
only a container a previous release minted matches, since nothing creates
those names any more.

**One path namespace.** The model only ever sees host paths (prompt workspace
root, middleware path normalization, deepagents' skills prompt), so the sandbox
mounts the workspace, out-of-workspace skill roots (ro), and shared sources at
their host paths too — `/workspace` is an alias, not the canonical root. Never
"fix" a sandbox path issue by teaching the prompt or middleware container-only
paths; extend the mount plan (`builder._resolve_sandbox_shared_mounts`,
`OlanoDockerBackend._base_run_args`) and bump the signature `schema` if
`_base_run_args` changes what an existing persistent container is missing.
Scenario coverage lives in `tests/integration/test_sandbox_path_namespace_live.py`.

**The skills scan reads the host, not the sandbox.** deepagents builds
`SkillsMiddleware(backend=<the agent's backend>, sources=...)` inside
`create_deep_agent` and loads `skills_metadata` once per thread, in
`before_agent`: one `ls` per source plus one `download_files` per SKILL.md,
and on `OlanoDockerBackend` each of those is a `docker exec` (110-250 ms
each; 7-17 s for the first turn of every thread on a box with 38 skills,
measured on a managed box and reproduced locally with `fake:instant`).
`builder._ensure_skills_host_scan_patch` rebinds `deepagents.graph.SkillsMiddleware`
to a same-named subclass whose constructor swaps a docker backend for a host
`FilesystemBackend(root_dir="/", virtual_mode=False)`, which is correct
precisely because of the paragraph above: the skill roots are host directories
mounted path-identically, so the host read lists the same directories and
advertises the same SKILL.md paths, and the agent's own `read_file` of a skill
still runs in the sandbox. The class keeps its name because deepagents matches
the skills slot by `name` (the class name). `LIONCLAW_SKILLS_HOST_SCAN=0` restores
the sandbox scan; `tests/test_skills_host_scan.py` pins the rest.
The same subclass also reads the files **once per process, not once per
thread**: its `before_agent` keeps the loaded list in `_SKILLS_LIST_CACHE`
keyed on the source directories and a fingerprint of every
`<dir>/<skill>/SKILL.md` (name, mtime_ns, size; one `stat` per skill), so a
new thread costs a few stats and gets its own copy of the list, and an
installed, edited or removed skill moves the fingerprint and is read on the
next thread. deepagents' own loader and parser still do the reading, so the
list is byte-for-byte what upstream would have built; the cache is skipped
for a backend whose files are not host files (a `StateBackend`, a remote
sandbox) and under `LIONCLAW_SKILLS_LIST_CACHE=0`. Two things the hooks must
keep: the `(state, runtime, config)` signature with `config: RunnableConfig`
(langchain injects `config` only when the annotation says so; typed `Any` the
hook is called without it and every first turn dies), and the per-thread
snapshot semantics (a thread that already holds `skills_metadata` is left
alone, so the "skills added since this chat began" notice keeps working).

## Dashboard: verify at both viewports

Any change under `olano/dashboard_2.0/src/views/**` or `src/styles/**` must be checked at both the desktop and mobile breakpoints before merge:

```bash
# needs the dashboard's npm tree: cd olano/dashboard_2.0 && npm install
uv run python .claude/skills/olano-tester/verify_dashboard.py --launch --viewport both
```

and eyeball the paired screenshots. Run it with `uv run` (or an activated venv) — a bare `python` misses Playwright and the harness, and without `node_modules` the Vite server never starts, so **both failure modes look like a red run rather than a missing prerequisite**.

The e2e suite (`make test-e2e`) already runs every `page`-fixture test at both viewports (`tests/e2e/conftest.py:VIEWPORTS`); don't pin a test to one viewport (`@pytest.mark.parametrize("page", ["desktop"], indirect=True)`) without a comment saying why.

New dashboard routes get an entry in **`tests/e2e/route_checks.py:ROUTE_CHECKS`** — the single list read by both `tests/e2e/test_route_checks.py` (what CI runs) and the skill above. Prefer a selector keyed on the section's own content over one that only proves the shell mounted, and prefer body text unique to one card over a heading two cards can share: the checks run in Playwright's strict mode, so an ambiguous selector fails as loudly as a missing one. The `e2e` workflow runs this suite on any PR touching `olano/dashboard_2.0/**`, `olano/runtime/**`, `tests/e2e/**` or the skill, so a UI move that strands a selector fails on the PR that causes it.

The same module owns the **app-shell contract** — `SIDEBAR` / `HAMBURGER` and `open_mobile_nav()` / `close_mobile_nav()` — for the same anti-drift reason: three suites drive the mobile drawer, and they had three copies of "click the hamburger, wait for `.app-shell.mobile-nav-open`". Drive it through the helpers rather than re-typing the selectors. A failed `page` test drops a screenshot, the DOM and the console into `.olano-tester/failures/<test id>/`, which is the path the workflow uploads on failure — before that, a browser-only failure reached us as a one-line Playwright timeout and nothing else.

### A popover's own CSS cannot know where its trigger is

Every dropdown anchored to a control that can wrap, collapse or sit near a viewport edge goes through **`ui/AnchoredPopover`** (over `ui/anchoredMenu.ts`): portal to `<body>`, position from the trigger's measured rect, clamp into the viewport, `auto`-flip above when there is no room below, cap `max-height` at the room on the chosen side, own the outside-click/Escape dismissal. A pointer-positioned right-click menu goes through **`ui/ContextMenu`**, which clamps the same way. Do not hand-roll `position: absolute; top: calc(100% + 6px); left/right: 0` again.

`.chat-header` is the reason: it is a `flex-wrap: wrap` chip row, so on a 390px phone a chip lands wherever the wrap puts it, and a 330px panel pinned with `right: 0` started at **x = −216** — the MCP status popover, mostly off the left edge. The model/effort menus were the same defect mirrored (`left: 0`, off the *right* edge); their `max-width: 80vw` capped the width and never touched the position. `tests/e2e/test_chat_header_popovers.py` asserts every header dropdown's box lies inside the window, at both viewports.

Two things this asks of the panel's CSS. The class is **chrome only** — position, width and height are inline, from the measurement. And the height clamp works only if the scrolling child can shrink: the panel gets `overflow: hidden`, its list gets `flex: 1 1 auto; min-height: 0` (without the `min-height` a flex child keeps its content height and spills past the clamp instead of scrolling inside it). Note also that a portaled panel is **no longer a DOM descendant of its trigger**, so a test selector scoped to the trigger's wrapper stops matching — give the panel its own `testId`.

## Dashboard UX: every field ships with a full explanation

Any user-configurable control in the dashboard — connector forms, config forms, the agent edit UI, onboarding — **must** carry a help/hint description detailed enough that a user who has never read the code can fill it in correctly. "Too short" is a defect; missing is a bug. A field's description must state, in plain language:

1. **What it does** — which runtime behavior the value changes, not a restatement of the label.
2. **The exact accepted format(s)** — with a concrete example (e.g. "numeric Telegram user IDs like `123456789`, or `@usernames`"), and how lists are entered (one per line or comma-separated).
3. **The default when left empty** — what the backend does with an unset key ("Empty allows anyone…", "Leave empty to use the bundled bridge").
4. **Interactions and caveats** — other fields it combines with, external platform toggles it depends on (e.g. a @BotFather setting), and anything that silently disables it.
5. **Every dropdown option** — `select` controls render only option labels, so the field's help text must explain what *each* option does and which one is the default (see the WhatsApp "Group listening" field for the pattern). The first `select` option must describe the backend default per the `options` contract in `connectorCatalog.ts`.

**An error's fix-it button follows the same rule.** `views/chat/ErrorRemediation.tsx` renders **nothing at all** for a remediation without an `action`, so a backend rule in `core/actionable_errors.py` that carries only a `summary` ships a message telling the user what to do above no way to do it. `kind` and `action` are independent — `kind` drives the chat-channel text tail (`REMEDY_NONE`/`REMEDY_RETRY` suppress it), `action` draws the button — so a `REMEDY_NONE` rule still needs an action to be visible in the dashboard. Never put a `label` on the action: the component localizes it, the backend cannot. Every action type must also degrade where its target does not exist — the same component is mounted by `cortex/AutonomyPanel` and `cortex/ThinkDrawer` for background runs with no chat — rendering a sentence rather than a button that cannot work, exactly as the member/credential branch already does. And mind `_provider_name(None)`: it is the lowercase "the model provider", fine mid-sentence and wrong as a message's first word, which matters because `/api/chat/stream` classifies with no provider.

Descriptions are **verified against the backend adapter** (`olano/platforms/*.py`), never guessed — the help text is a contract about runtime behavior, and a wrong description is worse than none. Connector field definitions live in `olano/dashboard_2.0/src/views/agents/connectorCatalog.ts` (`help` renders as a wrapping hint under the input, so length is fine); the same catalog feeds the connector panel and the onboarding wizard, so one edit covers both. When you add a field, config key, or option anywhere in the dashboard, writing this description is part of the change, not a follow-up.

## Knowledge base maintenance

Four knowledge documents plus five platform skills, split by **who is allowed to read them**. That, not the size of the change, decides which ones you update.

| Document | Source | Audience | Ships to customers? |
|---|---|---|---|
| **User guide** | `docs/user-guide/` (one page per section; `mkdocs.yml` is the nav). `scripts/gen_user_guide.py` concatenates the pages into `olano/archetypes/knowledge_user_guide.md`, which is **generated, never edited**; `tests/test_user_guide_generated.py` fails when it is stale | Deployment operators (docs.olano.ai: `docs.yml` writes `gh-pages`, `edge` from `main` and `X.Y` + `latest` from each release, and the `olano-docs` App Platform static site serves that branch), and AgentFather building agents from natural language | **Yes** — seeded to `<workspace>/system/knowledge/USER_GUIDE.md`, RAG-indexed, quotable by the agent on any channel |
| **Platform skills** | `olano/skills/built_in/olano-{platform,agent,cloud}/SKILL.md` | Every agent (procedures: the map of the platform, how to act inside it MCP-first with `self_*` + `magic_link_*`, cloud/credits/usage) | **Yes** — synced into `<home>/skills/` and advertised in every prompt |
| **AgentFather playbooks** | `olano/skills/built_in/olano-{admin,agent-builder}/SKILL.md` | AgentFather only — `requires_tools: [olano_list_agents]` gates them out of every other agent's prompt | **Yes**, on disk everywhere; visible only to agents holding the admin tools |
| **Architecture** | `docs/olano-dev/knowledge/knowledge_architecture.md` in the private `olano-ai/cloud` repo | Us | No |
| **Commands** | `docs/olano-dev/knowledge/knowledge_commands.md` in the private `olano-ai/cloud` repo | Us | No |
| **Troubleshooting** | `docs/olano-dev/knowledge/knowledge_troubleshooting.md` in the private `olano-ai/cloud` repo | Us | No |

The skills are procedures, the guide is the reference: a skill names the tool and the order, the guide holds the field tables and defaults, and neither restates the other. Platform skills live **only** in `olano/skills/built_in/` (never in the `olano-ai/skills` catalog) because they teach the tool surface of the installed version.

### Which one do I update?

Usually **both sides**, saying different things about the same change. A new `agent.json5` field gets its accepted values, default and purpose in the user guide, and its resolution order, validators and failure modes in `knowledge_architecture.md`.

- **User guide** — whenever the change is user-visible: a new or renamed dashboard tab or field, a new/changed/removed `agent.json5` or `config.yaml` key, a changed default, a new feature or connector, a new slash command, a new model tier, or a new user-facing error worth a troubleshooting entry. Writing that update is part of the change, not a follow-up. Edit the page under `docs/user-guide/` (a new dashboard tab gets `dashboard/<tab>.md` plus a `mkdocs.yml` nav entry and a row in `dashboard_2.0/src/core/docsLinks.ts` so Help deep-links to it), then run `uv run python scripts/gen_user_guide.py`; `uv run mkdocs build --strict` is what the Docs workflow runs, so a broken page link fails there too. **Screenshots** on those pages come from `uv run python scripts/capture_docs_screenshots.py [name ...]`, which seeds a fictional four-agent team into a throwaway dashboard through the e2e harness (no keys, no model calls) and writes `docs/user-guide/assets/screenshots/<name>.webp`; re-take the shots a visible dashboard change affects, and keep them clear of anything the guide may not show (the Config shot is scrolled past the model cards for that reason). `tests/test_user_guide_assets.py` fails on an image a page names that does not exist, a screenshot no page uses, or a mismatch with the script's list. **Diagrams** are ```` ```mermaid ```` fences (wired by `docs/mkdocs_hooks.py`, so `mkdocs.yml` stays `safe_load`-able); the agent's single-file copy keeps them as text and drops every picture.
- **Platform skills** — whenever an agent-facing procedure changes: a new or renamed `self_*` / `magic_link_*` / `olano_*` tool, a changed wiring order, a new mode an agent must reason about. Same commit as the tool.
- **architecture** — data flow, environments, tools, config fields, memory, scheduler, channels, security, prompt assembly.
- **commands** — CLI commands, dashboard sections, agent edit/config UI. **The CLI is documented here and nowhere customer-facing.**
- **troubleshooting** — user-visible errors and behaviours, and how they were diagnosed.

The internal three live in the private `olano-ai/cloud` repository (`docs/olano-dev/knowledge/`), not in this one, so they are free to stay as detailed as they are; a change here that needs them updated gets a companion commit there.

### The user guide and the skills never mention the CLI

An agent must never run or recommend the `olano` / `lionclaw` command line: a person in a chat has no shell, and every platform task has a built-in tool (`self_*`, `magic_link_*`, `olano_*`) or a dashboard tab. `tests/test_user_guide_policy.py` pins it — no backticked `olano <verb>` in the guide or the `olano-*` skills — and pins that the guide names the tool families it exists to emphasise. The same rule applies to archetype prompts (`agentfather.json5` included).

Magic links are the default for anything that needs a browser (connectors, MCP sign-in, a key into the vault, a messenger by QR, a file edit, the dashboard on a phone): the family is bound to every agent under the `magic_links` autonomy capability (`config/autonomy_defaults.py`, a second map next to `SELF_CONFIG_TOOL_CAPABILITY`), with the same off switches as every other implicit grant — per-agent `disabled_tools` (Tools tab / `olano_update_agent`), `default_internal_tools: false`, Config → Agent self-configuration, the per-agent Autonomy override — plus the call-time `_capability_gate` in `magic_link_tools.py`. Customer-service agents inherit it off.

### The user guide is the only file that reaches a workspace

`installer._scaffold_system_static_files` writes exactly one entry under `system/knowledge/`, and that is the **only** code that puts content there (`config/workspace.py` and `sync_system_zone` create the directory but write nothing into it). Both provisioning (`scaffold_agent_workspace`) and upgrade (`sync_system_zone`, via `olano update` / `olano agents refresh`) go through it. The upgrade path also **deletes** the three legacy files an older release seeded (`_LEGACY_KNOWLEDGE_FILES`, an explicit list — an operator's own document there survives), and the builder indexes `system/knowledge/` with `sync_directory(delete_removed=True)` so a purged file leaves the `knowledgebase` collection on the next boot instead of staying quotable forever.

A skill that assumes a toolkit declares it: `requires_tools:` in `SKILL.md` frontmatter (`skills/loader.py:compute_gated_skills`) hides the skill from every agent whose effective tool set lacks a listed tool — the same four enforcement points as `disabled_skills` (prompt filter, `delegate_task` registry, `iter_agent_skills`, the `/tools` banner), listed as *gated* with the missing names rather than switchable. It is how the AgentFather playbooks stay out of every other agent's prompt without a per-agent denylist.

Adding a second entry puts that file on every customer box. `tests/test_installer.py::test_scaffold_seeds_only_the_user_guide_into_system_knowledge` asserts the directory holds `USER_GUIDE.md` and nothing else, across both paths — it is guarding a confidentiality boundary, not a naming convention.

Do not bring the internal three back into this repository: it is public, and `[tool.hatch.build.targets.wheel] packages = ["olano"]` means anything under `olano/` additionally ships in the wheel whether or not it is ever seeded. That is how 1.07 MB of module paths, trust-model bypass analysis and defect history once reached every install.

### What must never appear in the user guide

Internal module paths or function names · trust-model or bypass analysis · defect history · model pricing, credit rates or multiplier factors · which infrastructure provider backs managed deployments · per-deployment economics · the provider/model identity behind the `olano:*` tiers (routing is deliberately opaque so it can change) · cloud plan names, machine sizes or credit allowances (the offering changes; point at cloud.olano.ai).

Describe **behaviour and the surfaces that control it**, never the implementation.

The trap this used to guard against is gone: the top tier's display name and its config value are both **Max** now (`olano:max`). The old id `olano:reasoning` was **retired, not aliased**, so a doc that still teaches it produces configs that fail to load — exactly the failure this line used to warn about, with the two spellings swapped. Note that `reasoning_effort` is unrelated and keeps its name.
